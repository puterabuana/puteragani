Designing for Mistakes - A Better Error Pattern

P
Putera Buana Gani
October 3, 2026 7 min read
Page 3 of 3
Photo: Unsplash / Design iteration

Error states become easier to design when they are treated as task states, not decorations added at the end. Start with a real journey: what was the person trying to finish, where could it fail, and what would a successful recovery look like?

The answers should shape copy, controls, persistence, and testing together. A reassuring sentence is useful only if the product actually preserved the work it claims to preserve.

Questions for Every Error State

01Can the person tell what failed without decoding a technical message?
02Is entered work still available after the failure or a page refresh?
03Is there one clear action that moves the task forward?
04Can the message be found and understood without relying on color alone?

Write for Action

Error copy should be specific enough to help and short enough to scan. Name the object that needs attention. Explain a fix only when the system knows the fix. If the system does not know, say what is known and offer a reliable alternative, such as retrying later or saving a draft.

Internal codes can still help support teams, but they should not be the primary message a person sees. A code like ERR-42 does not tell someone whether a payment was taken, whether a file was uploaded, or whether it is safe to try again.

Keep the User's Place

Recovery should return a person to the task rather than restart it. Keep field values when validation fails. Preserve draft text through a connection problem. After a failed upload, offer a retry without forcing the user to browse for the file again when the browser still has access to it.

When state cannot be preserved, explain that limitation before the risky step. Trust grows when the interface's promises match its behavior.

Test the Unhappy Paths

Design reviews often focus on the polished path. A useful test deliberately interrupts it: submit a missing field, lose a connection, press Back midway, open the page in a narrow viewport, and try again with a keyboard. Each scenario reveals whether the recovery path is real or merely described.

Observe how quickly someone understands the problem and resumes progress. If they must start over, hunt for an explanation, or ask another person what to do, the error state still needs design work.

Make Confidence Possible

People will continue to make mistakes. They will also change their minds, misunderstand labels, and encounter conditions the product did not anticipate. The goal is an interface that remains useful through those moments.

Good recovery design gives people a calm answer to three questions: What happened? What did I lose? What can I do now? When those answers are clear, an error becomes a temporary detour instead of the end of the journey.
